---
description: "taskIO — lire le PRD validé, poser les questions utiles, générer les tickets"
---

Applique les règles taskIO (`.claude/skills/taskio` ou `.cursor/rules/taskio.mdc`). Suis ces étapes, dans l'ordre, sans en sauter.

0. **Cible des tickets** (une fois par projet) : lis `.taskIO/config.json`. Si `fluentTickets.enabled` vaut `true` ou `false`, le choix est fait : passe à l'étape 1. Sinon (absent ou `null`), une question à la fois (même outil qu'à l'étape 4) :
   1. « Où envoyer les tickets ? » : fluent-tickets staging (`https://fluent-tickets.cinco-mg.ai/mcp`), fluent-tickets production (`https://fluent-tickets.cinco-mg.ai/mcp`), ou fichier JSON Linear seulement. Ce dernier choix → `npx taskio setup --ai <agents> --fluent-off`, puis étape 1.
   2. **Connexion**, dans cette session : préviens le dev que le navigateur va s'ouvrir (se connecter, choisir l'organisation, accès « Read and change », Autoriser), puis `npx taskio login --url <url choisie>` (délai de commande : 10 min). Il affiche l'organisation connectée (`slug`) ; fais-la confirmer, sinon relance `login`. Si la commande échoue faute de navigateur, donne au dev `! npx taskio login --url <url>` à taper lui-même.
   3. **Projet** : `npx taskio fluent teams --url <url>` → propose les projets en choix (nom et clé). Aucun ne convient → le projet se crée dans l'app web, puis relance.
   4. **Epic de repli** (facultatif ; disponible sur staging) : `npx taskio fluent epics --url <url> --team <clé>` → propose-les, plus « Aucun ». Il ne sert que si `tickets.json` n'a pas d'`epic` (l'epic du lot, créé au besoin à l'export, est prioritaire) ; le champ `project` d'un ticket reste un override.

   Puis `npx taskio setup --ai <agents> --fluent-org <slug> --fluent-team <clé> --fluent-url <url> [--fluent-epic "<epic>"]` : le code écrit `config.json`, ne l'édite pas toi-même. `<agents>` : `claude` si `.claude/commands/taskio.init.md` existe, `cursor` si `.cursor/commands/taskio.init.md` existe (séparés par une virgule).

1. **PRD** : regarde `.taskIO/prd/`. Un seul fichier (md, html, pdf) à la racine → `npx taskio parse .taskIO/prd/<fichier>`. Plusieurs fichiers à la racine → un seul PRD : `npx taskio parse .taskIO/prd/` (assemblés par ordre alphabétique ; préfixer `01-`, `02-` pour fixer l'ordre ; les sous-dossiers ne sont pas inclus). Plusieurs sous-dossiers → chacun est un PRD : demande lequel, puis `npx taskio parse .taskIO/prd/<sous-dossier>`. Si la sortie indique `"reused": true`, propose de reprendre ce run (et ses `answers.json`) plutôt que de tout refaire.
2. **Lecture** : lis `prd.normalized.md` du run.
3. **Questions** : liste trous, ambiguïtés, contradictions. Ne garde que celles dont la réponse change les tickets ; aucune dont le PRD donne la réponse. Ajoute toujours la question `methodology` (TDD, BDD, Spec driven, Tests après le code, Prototype d'abord, + « Autre »), avec avantages et inconvénients (si `defaultMethodology` du `parse` n'est pas `null`, présente-la comme recommandée). Écris `questions.json` (gabarit : `.taskIO/templates/questions.md`) puis `npx taskio validate`.
4. **Poser une question à la fois** : Claude Code → outil de question natif (choix + « Autre »). Cursor → un message par question, choix numérotés, réponse par numéro ou texte court. Après chaque réponse, mets à jour `answers.json` (une réponse par question ; la méthode est la réponse à `methodology`) (reprise possible).
5. **Récapitulatif** : affiche toutes les réponses, la méthode et les hypothèses que tu vas appliquer. Demande validation ; permets de modifier une réponse. Passe `validatedByHuman` à `true` puis `npx taskio validate answers.json`. **Aucun ticket avant cet accord.**
6. **Générer** : écris `tickets.draft.json` (gabarit : `.taskIO/templates/ticket.md`), en respectant le découpage minimal, la méthode choisie, une estimation par ticket et une estimation globale justifiée. Si le `parse` signale des `assets` (captures, gabarits HTML, liens Figma), lis `assets.json` du run (et regarde les images) : rattache à chaque ticket **uniquement** les assets de sa fonctionnalité (images et HTML → `attachments` avec le `path` du manifeste, lien Figma → `links` avec son `url`) et rien si aucun ne correspond ; sinon, pour d'autres maquettes ou fichiers de `.taskIO/prd/`, même principe (`links`, `attachments`) ; un livrable qui fait partie d'un autre devient une sous-issue (`parent`) ; le Markdown de référence va dans `documents`. Voir « Fonctions fluent-tickets » dans les règles. Regroupe le tout en lot cohérent : un `epic` pour le PRD et, si le projet est assez gros, des `milestones` ordonnés (règle « Lot cohérent » ; chaque ticket dans un jalon, prérequis dans le même jalon ou un jalon précédent).
7. **Contrôler** : `npx taskio validate tickets.draft.json`. Corrige ; `validate` compte les échecs (`validateMaxAttempts`) et renvoie le code 3 à la limite : arrête-toi alors et montre les erreurs au dev. Traite les avertissements (corriger ou justifier).
8. **Assembler** : `npx taskio assemble tickets.draft.json` → `tickets.json` (enregistre aussi la clé de cache). Renseigne avant `npx taskio meta <run> --agent <claude|cursor> --model <id>` si connu.
9. **Revue** : affiche la liste (titre, estimation, dépendances) et l'estimation globale avec sa justification. Le dev choisit : valider (`npx taskio approve <run>/tickets.json` pour tout, ou `… approve <fichier> <id…>` pour certains ; **n'édite jamais `tickets.json` à la main**) ou donner des retours (→ `/taskio.revise`).
